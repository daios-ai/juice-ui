# Installation & filesystem convention — the juice family

Every juice-family binary (`juice`, `juice-ui`, `juice-agent`, …) keeps its state
under **one root, one subdirectory per component**, so they coexist and the whole
suite backs up or relocates as a unit.

```
$JUICE_HOME                       (default ~/.juice; env-overridable, same on macOS)
├── bin/                  the family's executables, where the installer puts them
├── worlds/<world>.json   one network's definition: its money, and its seeds
├── kernels/<world>/      one kernel per world: juice.db, config.json, the rail
│                         key and its records, serve.lock, cache/
├── client/               config.json (the kernels this client knows, and which
│                         login is selected), credentials/<handle@kernel>.json
│                         (one session each, 0600)
├── ui/                   config.json, state.json, kernel.log (the first boot's)
├── agents/<name>/        one agent's configuration, persona, memory
├── services/<name>/      one installed service; services/chat/ is juice-chat's,
                          holding config.json, state.json, rooms.db, serve.lock
└── supervisor/           the process supervisor: programs/<name>.json, one per
                          program; log/; run/; supervisor.lock
```

This is the layout `juicedocs/ecosystem-standard.md` binds every juice program
to. The UI keeps only `ui/`; it *reads* the `kernels` half of
`client/config.json` to resolve the kernel it names, and touches nothing else.
In particular it never reads or writes `client/credentials/`: those are the
operator's own logins, and this UI authenticates browser people and holds each
one's tokens in its own server-side session.

`bin/` holds no state: the programs are replaceable, so an installer
overwrites them and a person deletes them without losing anything. A component
looks for a sibling program there; the agents app finds `juice-agent` in
`$JUICE_HOME/bin` before `PATH` (`JUICE_AGENT_BIN` overrides both), and the chat app
finds `juice-chat` the same way (`JUICE_CHAT_BIN`).

Rules each repo follows:

1. Read `JUICE_HOME` (default `~/.juice`); keep all state under
   `$JUICE_HOME/<component>/`.
2. **Fixed default, never cwd-relative** — attach to the same state wherever
   launched.
3. The binary `MkdirAll`s its own subdir (`0700`) before first write.
4. The installer touches only the executables in `bin/` (`mkdir -p` +
   `install`, plus `uninstall`); never a component's state.
5. **Same role → same filename across every component** (the subdir is the
   namespace): `config.json` (operator, hand-written), `state.json` (machine
   state), `tokens/` — never a component-prefixed name like `juice.json` or
   `juice-ui.json`. Databases are named for their content (`chat.db`).
6. Migrate keep-old-if-present: never auto-move a key or live DB; log a one-line
   manual move.

Single home (Geth/IPFS/Cargo lineage) over the XDG split: this state is precious,
not purgeable, and one relocatable root beats three scattered trees.

**juice-ui** is conformant (`$JUICE_HOME/ui/`, creates its own dir, fixed default).
It is installed in two stages, the way a desktop product is:

1. **`install.sh`**, the bootstrap, puts this repository's three programs
   (`juice-ui`, `juice-chat`, `juice-supervisor`) in `bin/`, from one release
   tarball verified against the release's checksums, and runs
   `juice-supervisor setup`. `make install` places the same three from a build.
2. **juice-ui installs its components** on its first start, in the installer's
   first step, from one list in `kernel/kernel.go` (`Components`): the kernel
   (`juice`) and the agent (`juice-agent`), each at the release this UI was
   verified against, by the routine the family's installer follows (the
   platform's asset, refused without a matching SHA-256, tried with `--version`,
   renamed into `bin/`). A component missing from `bin/` is installed; one older
   than its release is replaced only in a fresh installation, one whose
   `kernels/` holds no kernel; otherwise nothing present is replaced, since a
   newer kernel may refuse a home an older one made, and upgrading under an
   existing kernel is the operator's act. An override variable
   (`JUICE_AGENT_BIN`) leaves its component to the operator, and a UI configured
   for a kernel elsewhere installs nothing. The installer then creates this
   installation's kernel under `kernels/<world>/`, or starts the one there.

The first boot's output goes to `ui/kernel.log`, and every program's to
`supervisor/log/`; the recovery phrase is generated by the UI and never written.
